The designer who was afraid of code

How a graphic designer who swore code wasn’t for him ended up a senior developer, and why design still shapes how I build.

My first job had nothing to do with design or code. I worked in IT recruitment in Wrocław, searching databases and phoning candidates, trying to find developers for other companies. I spent over two years doing it. I never once imagined I would become one.

Code was for developers

In 2008 I started as a graphic designer at an advertising agency. Brand work, print, marketing materials, email campaigns for clients like BMW and MINI. Some of those campaigns and websites needed HTML and CSS, so I wrote it. Not because I wanted to, but because someone had to and I was there.

I was very clear with myself about where the line was. I was a designer. Code was a job for developers. If you’d asked me back then, I’d have told you I didn’t like coding at all.

For the next few years, first in Poland and then after moving to the UK, I kept designing. Freelance work, then in-house roles. Layouts, brand assets, marketing pages. And, more and more often, building the websites I’d designed, because it was quicker than handing them over and explaining what I meant.

The thing that changed my mind

It wasn’t the code itself that hooked me. It was what happened after.

A design file sits on your screen. Only you and the client see it. A website is different. Someone else opens it, clicks through it, uses it. The thing you drew is suddenly alive, and it’s out of your hands.

Once I’d felt that a few times, I wanted more of it. Each project I spent a bit less time drawing and a bit more time building. In 2018 I made it official and became a front-end developer.

What I brought with me

Design gave me one habit that never left: an eye for detail.

I can’t always explain it. I just see when something is off. Spacing that isn’t quite even. A font a size too big. A button that’s slightly out of line with the text above it. A form that’s harder to fill in than it should be. It bothers me until it’s fixed.

It turned out the same thing happens with code. Messy code bothers me in the same way a misaligned layout does. I wanted mine to be clean, consistent, and easy for the next person to read. Good design is mostly about care for whoever comes after you, the user or the next designer opening the file. Good code is the same.

WordPress, then the back end

Front end led to WordPress, properly this time. Not just setting up themes and plugins, but writing my own: my first plugins, custom functions, fully custom builds. Then WooCommerce, with its own checkout flows, shipping logic and integrations, where small details decide whether someone finishes paying or leaves.

That was the point where I stopped being a designer who could code and became a developer who could design. The interesting problems were no longer only on the screen. They were in the data, the queries, the logic behind the page.

Everything has its place

I tried CodeIgniter for a while. It was a short story.

Laravel came along almost by accident. What caught my attention first was practical: I didn’t have to write everything myself. But what kept me was something else. In Laravel everything has its place. Routes, models, controllers, views, each one where you’d expect it. Open a Laravel project you’ve never seen and you can usually find your way around.

That’s exactly what good design does. A clear structure, a consistent system, nothing left lying around. It felt familiar.

My first real Laravel project was a rebuild of the asset management system at the company I work for. It started as a training project, something to learn on. It taught me more than any tutorial.

A pocket Stack Overflow

Then the first AI models that could write usable code arrived. At the start I treated them like a pocket Stack Overflow. Ask a question, get a snippet, check it, adapt it.

That changed quickly. Today I work with coding agents that write whole features under my rules, my tests and my review. Which brought me back to the same old question, just in a new place: how do I know the result is right?

So I do what I’ve always done. Reproduce, measure, fix the cause. I’ve started testing what actually makes these agents reliable, and writing up what I find. The first study ran 1,080 times across three models to see what happens when you tell an agent to skip the tests.

Still a designer

Today I’m a senior web developer working across the stack, from WordPress and Laravel to Next.js and AI agents. It’s a long way from writing HTML only because someone had to.

But design is still where I start. When I look at a page, a pull request or an agent’s output, I still notice when something’s off. I think that’s the most useful thing I brought with me, and the reason I don’t want to leave it behind.

If you’re a designer who’s sure code isn’t for you: I was too. Build one small thing and see someone else use it. That’s what got me.
