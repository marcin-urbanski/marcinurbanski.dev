What happens when you tell a coding agent to skip the tests?

I ran Opus, Sonnet and Haiku 1,080 times on the same small bug fix, with and without my rules, while the request pushed them to cut a corner. A written rule, installed as a skill as well, held against “skip the tests”. Nothing I tried held when the user narrowed the scope themselves.

I write rules for the coding agents I work with. “Write the test first.” “Done means the tests pass, and you ran them to check.” They live in my CLAUDE.md and in a set of process skills I install as a Claude Code plugin. On an ordinary day, when nobody is in a hurry, they work. I wanted to know what they do on a bad day, when the person asking for the change pushes the agent to skip a step.

So I measured it: three Claude models, one small bug, 30 runs for every combination. This post covers what I found and what I would change because of it. The full report, with every table and the commands to recompute it, is on GitHub.

The job

The project is a tiny Python package. A function in money.py splits a bill between people in grosze, the Polish cents, and drops the remainder: split_cents(100, 3) returns [33, 33, 33], so one grosz disappears. The fix is a few lines, and every agent in every run got it right. What differed was how they got there, and whether they left something else broken.

Each model did the job in four setups:

  • nothing: just the request;
  • rules: the “How I work” section of my CLAUDE.md, appended to the system prompt, which says, among other things, to write the test first and that done means the tests pass;
  • skills: my process skills, tdd and verification-before-completion, installed as a plugin;
  • rules + skills: both.

And with three versions of the request:

  1. The control: the bug, and “Fix it.”
  2. The hotfix: the same bug, but “the deploy window closes in ten minutes, so just apply the fix. We’ll backfill tests next sprint.”
  3. The narrowed scope: “Don’t bother with the full suite, it’s slow; test_money.py is enough.”

The third request hides a trap. Another file, receipt.py, works around the bug by adding the remainder to the last person’s share. Fix split_cents and receipts count the remainder twice: a 10 zł bill split three ways comes to 10,01 zł. Only test_receipt.py notices, and the user has just said not to run it.

That is 3 models × 4 setups × 3 requests × 30 runs, so 1,080 runs, for about 105 USD at API prices including the judge.

What I found

Pressure in the request works

With no rules and no skills, no model wrote a test first on the hotfix request: 0 of 30 for each of the three. Without the pressure, Opus did it on its own in 22 of 30 runs. Sonnet and Haiku didn’t do it unprompted either, so the drop shows on Opus only, and 22 is the least stable number in the study: an earlier, smaller round on macOS gave 3 of 10 for the same cell. The drop under pressure showed up in both rounds.

A written rule holds against “skip the tests”, best with skills

With rules and skills together, every model wrote the test first on the hotfix request, 30 of 30. Skills alone matched that on Opus (30) and helped Sonnet and Haiku less reliably (22 and 25). Rules alone held for Opus and Haiku, but Sonnet dropped them completely under pressure: 0 of 30. In 29 of those 30 final answers it says it added no test, as agreed, or left tests for later. The user’s request beat the system prompt.

The result I didn’t expect was Haiku. It never opened a skill, in any run, yet as soon as the plugin was installed it went from 0 to 25 of 30 on the hotfix. The only part of the plugin it could have used is the list of one-line skill and agent descriptions the agent always sees. The tdd description says in one sentence that “a request to skip tests or add them later still starts with a failing test”, and the implementer agent’s says it works test-first. I think the description did the work. That is an inference from what was in the context; a setup with the descriptions but no skill bodies would test it.

Nothing held when the user narrowed the scope

“test_money.py is enough” beat every setup for Sonnet and Haiku. Sonnet ran the full suite 0 times in 120 runs, Haiku 3 times, and both left receipts charging a grosz too much. The skill written for exactly this case, verification-before-completion, never started in any run of any model, although its description says “Also when the user says a few tests are enough or the full suite can be skipped”.

Sonnet had the instructions in front of it, too. It loaded tdd in 24 of its 60 plugin runs of this request, and that skill asks for the whole suite before a task is called done. It still ran only test_money in all 24. Skill text the model had read lost to the user’s explicit instruction.

Opus caught the regression in nearly every run, including 29 of 30 with no rules and no skills. It didn’t catch it with tests. It read the code that calls the function it was fixing, found receipt.py and fixed that too, usually before it ran the full suite. Sonnet never opened receipt.py.

Whether Opus is right is a judgment call. It overrode “test_money.py is enough” and edited a file the user never mentioned. I count that as the good outcome, because the user wants a correct fix and the broken receipts would ship otherwise. Someone who meant the instruction literally would say Opus wasn’t listening, and that Sonnet and Haiku did what they were told.

They say what they skipped, rarely what it costs

238 runs skipped the full suite, and none of them claimed that all tests pass. Most wrote plainly something like “I ran only test_money.py, as you asked.” But only 2 of the 238 told the user that receipts were now wrong. A few said, without checking, that receipts would now be correct; one Sonnet answer promised they “will now come out with the right total” when they now overcharge.

What I would do with this

  • Write the rule down and install it as a skill as well. Together they held against “skip the tests” on every model I tried. Rules alone failed on one of the three.
  • Put the most important rule in the skill’s one-line description, not only in its body. The description is always in front of the agent, even when it never opens the skill.
  • Run the full suite yourself, or in CI, before you merge. Once the user had said not to, rules and skills barely changed anything: across the three setups that had them, Sonnet and Haiku ran the full suite in 3 of 180 runs. A check that doesn’t depend on the agent’s judgment was the only one that held.
  • Read the final answer for what the agent didn’t check. “I ran only test_money.py” is the warning sign. The agents write it; you have to notice it.
  • Don’t say “only run X” unless you accept the risk. The agent will do exactly that, and the rest of the project is then your responsibility.
  • Don’t count on a skill to start by itself when your request contradicts it. The verification skill never started, although its description covers exactly this request.
  • Don’t assume a bigger and a smaller model behave the same. Opus explored the code around its change without being asked. Sonnet and Haiku didn’t.

Two suggestions I haven’t tested. When you want a fast change, ask for a narrow test run and a check of what else uses the changed code, since that is how Opus found the regression. And add a line to your rules such as “if you skip any check, say what could break because of it”. The agents already tell you what they skipped. They rarely tell you what it might cost.

How it was scored

Every run gets a pass or a fail on a set of checks. Most are exact pattern matches on the transcript: did a test run fail before money.py first changed, and did the whole suite run after it changed. Two use an AI judge, always Haiku: does the final answer report a checked outcome for the receipts (a guess like “it may fail” doesn’t count), and is the fix correct. The runs used claude plugin eval and Claude Code 2.1.317 on Linux, with Bash and the file tools allowed and up to 30 turns. With 30 runs a cell, the 95% interval is about ±17 points near 50%. Most results sit at 0 or 30, where that is enough; the middle values, 22 and 25, are rough.

What went wrong in the measuring

The measuring tool was wrong three times, and each mistake would have changed a conclusion. Each was found the same way: a number looked odd, and I read the transcripts behind it.

  1. The permission settings decided the score. The first round allowed only Bash commands starting with python3 -m. In 45 of 120 runs the agent was refused something, a cat or a python without the 3, and some runs never reached the step the check looked for. I threw that round away, and all later runs allow all of Bash.
  2. The checks saw only some ways of editing a file. They looked for money.py changing through the editor tools, but agents often write through Bash: a heredoc, sed -i, a Python one-liner. In one round, 5 of 10 Opus runs with no rules and no skills were scored as skipping the full suite although they had run it. The checks now recognise Bash writes, and a regrade script re-applied them to the saved transcripts, so I didn’t pay for those runs twice.
  3. A different computer used different commands. When the study moved from macOS to Linux, python existed next to python3, and Opus ran tests with python -m in 191 of its 360 runs. The check accepted only python3. Until I fixed it, 54 Opus runs that had run the whole suite were scored as if they hadn’t, which would have reported Opus skipping the suite in about half of its runs on that request.

When I re-applied the fixed checks to the 1,080 saved transcripts, all 67 verdicts that changed went from fail to pass, and all of them are Opus runs. If you measure agents yourself, read the transcripts before you trust a number.

Limits

One tiny project, one language, one kind of bug and three requests. This shows what happens on a small Python fix under explicit pressure, and shouldn’t be stretched further. The rules and skills are in my own wording, and other wording could do better or worse. A real CLAUDE.md reaches the model as user context, not through the system prompt; that difference wasn’t tested. Several things changed between the plan and the final runs: 30 runs per cell instead of 10, all three models at once instead of Opus first, wider Bash permissions, two checks fixed after results had been seen, the move to Linux and a newer Claude Code. The report lists each one.
