TimeRabbit: the first app I built with a team of agents

How I partly handed over the wheel to AI agents working under my rules, what they did well, and what I still had to do myself.

TimeRabbit is a native macOS time tracker. It’s also the first app where I didn’t write most of the code myself.

I partly handed over the wheel to a team of AI agents. They worked under my rules: write the spec first, write the test before the code, get your work reviewed by someone else. I decided what we were building, set the standards, and checked the result. Thirty-two days after the first message I had a signed app I use every day.

This is what working with that team was like.

Why build it at all

At work I use automatic time-tracking software. It does the job, but two things kept bothering me. Tasks my colleagues added in Teamwork took hours to appear, until I synced everything by hand. And the interface felt like a developer’s app: there was a design idea, but it wasn’t carried all the way through. I wanted something that looked good and where you find what you need without stopping to think.

So I decided to build my own.

Meet the team

Every project with agents starts the same way it would with people: onboarding. Mine is a CLAUDE.md file and a set of process skills, the rules the team works by.

The team had clear roles:

  • The planner, the main session following a spec-first skill, turned each feature into a written spec and plan. Nothing got built until I’d approved it.
  • The implementer wrote a failing test first, then the code to make it pass.
  • The reviewer checked every change. It saw the task and the code, but not the implementer’s reasoning, so it had to judge what the change actually did, not what it was meant to do.

My job was everything they couldn’t decide for me: what the app should do, in what order, how it should feel. And testing it on a real Mac, every day.

The team was fast

The first working piece, recording what I do on my Mac, was committed about 45 minutes after I started. The Teamwork integration came half an hour later. By the first signed release the team had written about 1,600 tests, and today there are over 2,200. There is more test code in TimeRabbit than code being tested.

The hard part was knowing whether what came back actually worked.

The team didn’t know what I knew

My first question was which technology to use: NativePHP or Tauri, two ways to build one app for macOS and Windows. The agent picked Tauri, with good reasons: it needs a fraction of the memory. Then I mentioned I don’t own a Windows machine. Every computer I have is a Mac.

The answer changed straight away: if I can only test on a Mac, cross-platform is a promise I can’t check. We went native, with Swift. The whole U-turn took six minutes.

The agent had the reasoning. I had the context. That turned out to be true for the whole project.

“Done” didn’t always mean done

I asked for a small thing: clicking Today should scroll the timeline so the current time is in the middle.

By then the team could already see the app. Earlier in the project I’d given them a script that launches it and takes a screenshot, and a rule to run the app and check the result themselves instead of telling me it’s done. The agent did both. One screenshot looked right. Another, taken with the clock at 16:40, showed the timeline at 7:30–9:10. The agent found a plausible explanation, marked it “not verified”, and the change was reviewed and merged with every test green.

On my Mac it didn’t work. At 16:40 the window was centred on 8:20, halfway between midnight and now.

Passing tests are evidence, not proof. That’s the same lesson as my study on skipping tests, from the other side. And a screenshot that contradicts the result isn’t something to explain away. It’s a reason to stop.

A rule only counts where it’s written

At one point the reviewer was copying the whole project, build files included, every time it checked a change. The copies grew to around 60 GB, the disk filled up and all work stopped.

I fixed it. Six days later it happened again. The rule was in the implementer’s instructions, but not the reviewer’s.

Agents don’t pass knowledge to each other in the corridor. If a rule isn’t written where a team member will read it, it doesn’t exist for them.

Mistakes became team rules

Like with any team, the same mistakes kept coming back in review. So they became a coding standards document, and each rule keeps a count of how many times it was caught. The top one was comments that no longer described the code: 11 times. Two others were about time itself: a running timer counted as zero, an hour landing on the wrong day. Fitting, for a time tracker.

The project changed my skills too. The test-first rule now applies even to a “quick fix”, the full test suite runs even when someone says a few tests are enough, and every spec has to say how we’ll know it works.

The part I kept

Design I didn’t hand over.

The name came after rejecting dozens of ideas: TimeRabbit, after the White Rabbit from Alice in Wonderland, the one with the pocket watch who’s always late. The logo followed from it, a clock whose hands become the rabbit’s ears. I drew the concept by hand, and it became the app’s launch animation.

What I learned

Working with agents is a lot like working with a team. They’re quick, they follow the rules you give them, and they don’t know what you haven’t told them.

The code is the easy part now. My job was to decide what we’re building, write down how we work, and keep checking whether “done” really meant done. When it didn’t, the fix was rarely in the code. It was in the rules.
